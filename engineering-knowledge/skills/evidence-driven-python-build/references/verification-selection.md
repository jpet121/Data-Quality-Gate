# Select verification by risk

Project-required methods override this selection guide. Passing results support only their tested domain. Counts below are never prescribed globally.

| Method | Use when / risk addressed | Prerequisites | Evidence and limitations |
|---|---|---|---|
| Unit / functional | Deterministic rules, calculations, guards and business workflows changed. | Independent expected result from requirements. | Exact input/output assertions; mocks can miss real integration behavior. |
| Boundaries / malformed input | Parsers, codecs, size limits, nested data or precision-sensitive arithmetic. | Valid neighboring cases and declared rejection behavior. | Repro inputs and controlled errors; test every representation sharing a contract. |
| Property-based / Hypothesis | Large structured domains and general invariants justify generation/shrinking. | Constructive strategies, valid relationships, fixed regressions, bounded settings. | Actual examples/phases, seeds and minimized failures; sampling is not exhaustiveness. |
| Stateful | Histories, protocols, retry/replay or evolving stored state matter. | Explicit state model, isolation, preconditions and invariants. | Operation traces and observed state; modeled histories may omit crash recovery. |
| Differential | An independent simpler reference can establish expected semantics. | Approved requirements, calibrated oracle, normalization rules and shared-dependency assessment. | Actual attempted/executed/compared/replayed outcomes, divergences and crashes; a wrapper around production is not independent. |
| Fuzz / adversarial | Encodings, structure mutations and crash surfaces extend deterministic boundaries. | Authorized local target, limits, replayable inputs and expected failure categories. | Seeds, input identities, resource anomalies; generated quantity is not coverage. |
| Mutation | Need evidence that important tests detect plausible source faults. | Passing frozen baseline, isolated copies, actual test outcomes, project-specific acceptance if required. | Explicit denominator; separate killed/survived/invalid/setup-error/timeout/equivalent. No universal score threshold. |
| Fault injection | Partial operations, dependencies and recovery paths can fail. | Predeclared injected condition, positive/negative controls and observable failure/state. | Rollback/retry/side-effect assertions; synthetic calibration is not real business acceptance. |
| Real database / concurrency | Adapter behavior, transactions, uniqueness, atomicity or competing clients matter. | Disposable correctly isolated service, explicit readiness, deterministic barriers and independent connections. | Reopen/rollback/content-conflict/claim results; in-memory or SQLite parity does not prove another backend. |
| CLI / subprocess / serialization | Public entry points, errors and model round-trips changed. | Clean working directory and observable stdout/stderr/exit/state contracts. | Actual outputs and failures; use the specified exit semantics rather than inheriting another project's convention. |
| Runtime / dependencies / install | Supported versions, optional drivers or packaging changed. | Clean compatible environment, declared extras, retained TLS/checksums, dependency consistency. | Real installation/import/entry-point evidence; local editable imports can hide broken wheels. |
| Artifact / integrity / build | Generated executables, wheels, archives or external delivery matter. | Frozen source/artifact identities, complete member inventory, clean extraction and authorized destination. | Hash/member checks and execution of exact bytes. Matching hashes establish integrity, not reproducible builds, authenticity or correctness alone. |
| Formal model | High-value algorithmic/state properties have proportionate mathematical structure. | Explicit model, assumptions, real checker and required correspondence. | Checked proof artifacts, finite comparison and disclosed axioms. Model proofs are distinct from formal implementation equivalence. |
| Static / security / advisories | Trust boundaries, dependencies or dangerous operations changed. | Applicable scope, tool configuration and manual review of findings. | Raw findings/exit code and per-finding disposition; no silent suppression or universal security claim. |

Use explicit readiness conditions instead of arbitrary sleeps where possible. Bound workers and resource consumption to the actual toolchain. A resource-limit failure in the verifier is a harness/setup issue to diagnose, not an acceptable mutant kill or reason to weaken assertions. A trusted local testing harness is not automatically a hostile-code sandbox.
