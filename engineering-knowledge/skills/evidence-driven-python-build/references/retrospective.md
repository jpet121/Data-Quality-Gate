# Retrospectives and durable improvement

Recover only available history. Distinguish verified observations, explicit user decisions, engineering inferences, proposals and unresolved questions. Missing earlier conversation, source revisions or reference text must be listed, not reconstructed as fact.

For each significant failure retain:

**Defect → Reproduction Evidence → Root Cause → Repair → Regression Verification → Reusable Lesson**

Include authority/source location, affected interface, risk and the limits of the finding. Preserve unsuccessful runs and changed hypotheses. Harness and environment failures belong in the history with their real classification. Distinguish bugs newly repaired during this effort from repairs already in the uploaded baseline.

Extract mechanisms, not incidental constants: apply the same lexical contract through every nested representation; calculate exact invariants independently of ambient numerical settings; test actual backend return types and constraint conflicts; bound reads before allocation; preserve typed failures and complete serialized state; keep verifier failures observable. Specific money limits, database versions, test counts and archive layouts remain case facts.

Install three layers: short global principles, a focused skill with detailed references, and a separate project case study/evidence store. Inspect the actual Codex home, configuration, overrides and existing skills first. Prefer an equivalent existing skill. Back up changed files, preserve unrelated bytes, use idempotent marked blocks and detect conflicts. Never modify credentials or weaken tool/sandbox policy to make installation or discovery appear successful.

Verify written bytes, metadata, references and owned-file inventory. Test meaningful installer behavior, repeated execution and conflict refusal where scripts are supplied. Test real fresh-process skill discovery and a fresh-session instruction load when supported; clearly distinguish parsing, discovery and model execution. Record platform scope and whether a filesystem snapshot or another device's installation was actually tested.

For each improvement record its supporting evidence, generalized mechanism, new guidance location, validation performed, scope and known limits. Keep obsolete project details outside global rules. Do not silently rewrite an already tested release to polish its narrative: record an erratum and its impact, and obtain any needed authority for a subsequent artifact revision.
