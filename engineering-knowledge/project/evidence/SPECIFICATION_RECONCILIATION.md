# Explicit source reconciliation for release review

The user authorized README.md, docs/ACCEPTANCE.md and examples/matrix_v1.json as the functional requirements alongside the two XML contracts, delegated the input-profile choice, and accepted the stated 16-mutant acceptance criterion. These decisions are recorded verbatim in specifications/OWNER_ACCEPTANCE_DECISIONS.json. No further application-specific XML is required for this designated scope.

1. **Money/timestamp wording:** retain the existing 13-integer-digit/two-fractional-digit money limit and strict calendar timestamp dialect. The owner delegated this choice; the requirements now state these limits explicitly. The original boundary tests remain unchanged.
2. **Nested money:** integer notation is a valid money lexeme. Nested JSON integer prices convert exactly to Decimal; booleans remain forbidden. Exponents and excessive fractional digits are rejected in both string and numeric representations. These repairs enforce the authorized money grammar, rather than introduce float coercion.
3. **Exact totals:** totals must match exactly, independently of ambient Decimal rounding settings. Integer-cent production arithmetic and a rational-arithmetic oracle enforce that requirement.
4. **No-stubs rule:** the Development contract prohibits unfinished required implementations. The authorized functional scope deliberately specifies disabled-by-default dispatch and a manually supplied in-memory sink. LocalStubSink fully implements that specified recording behavior; it is not a placeholder for an undisclosed production connector. Its legacy public name is retained. Live ERP/payment/carrier integration and lease crash reclamation remain explicitly outside this release scope.
5. **Network wording:** the README's no-traffic statement is interpreted in its pipeline/workflow context: validation and default dispatch make no business-system calls. The separately documented optional PostgreSQL adapter performs caller-requested database I/O. No implicit business connector is implemented, and no remote business endpoint was contacted. This contextual distinction is made explicit here instead of claiming that an explicitly requested PostgreSQL connection is impossible.
6. **Old reports and optional tests:** historical missing-Hypothesis/Python/PostgreSQL statements are execution history, not persistent prohibitions on verification. The user's release task makes Hypothesis, Python 3.12 and isolated PostgreSQL mandatory. All run in the complete gate; Profile A is diagnostic, not a substitute for that gate.
7. **Output format:** the current user requests a ZIP, matrix, evidence and manifest. That supersedes compiler-stage/raw-source-only presentation rules. The executable application is still provided as self-contained main.py; development and verification sources accompany it for review and reproduction.
8. **Approval authority:** user-approved requirements and mutation criteria are technical governance inputs. They do not themselves grant production release approval. The release evaluator withholds authorization until the user's final release decision is recorded.

No claim is made to universal correctness, formal Python equivalence, official LIGO certification, SLSA compliance, offline installation or external business-system readiness. Cryptographic collision resistance, the operating system and the documented Python/Lean runtimes remain explicit trust assumptions.
